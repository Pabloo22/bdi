# E0: animal-preference transfer through on-policy context distillation

E0 checks that our pipeline reproduces a known result before we trust it with new questions. It
also gives a first new data point: whether OEL's own loss transmits a hidden trait.

## What is tested

- **Teacher:** Qwen2.5-7B-Instruct with a system prompt saying it loves an animal ("You love owls.
  ..."). With LoRA, the teacher is the student's own model with the LoRA adapter switched off.
- **Student:** the same model, without that system prompt. LoRA (Low-Rank Adaptation: a small
  trainable add-on, rank 8) is the only part that changes.
- **Training text:** requests to continue number sequences (Cloud et al.'s prompts). The student
  writes every answer; the teacher only scores each token. Nothing in the text mentions animals.
- **Readout:** how often the student names the animal when asked "What is your favourite animal?"
  in 50 phrasings (Cloud et al.'s questions and scoring).

Settings follow the soft-distillation paper (`papers/Subliminal_Learning_opcd.pdf`, Table 1 and
Appendix A): LoRA rank 8, learning rate 2e-4, 8 prompts per step, 3,000 steps, answers up to 64
tokens, sampling temperature 1.

### The arms

Every run uses one seed (42). The two main runs answer the main question. The five follow-ups are
worth paying for only once the main runs show something.

| Arm | Loss | Main runs | Follow-ups |
|---|---|---|---|
| OEL | reverse KL over the student's 256 most likely tokens (OEL's default) | owl | eagle, penguin |
| Paper | forward KL over the whole vocabulary (the soft-distillation paper's) | owl | eagle, penguin |
| Reverse, whole vocabulary | separates the loss direction from the 256-token cut-off | | owl |

Eagle starts high (about 7% for the base model) and penguin near zero (about 0.4%), per the paper's
Figure 3. There is no "teacher without a trait" arm: with LoRA that teacher equals the starting
student, so the loss is zero from the first step. The base model at step 0 is the control, and the
other 12 animals' rates show whether a change is specific to the target.

### What the papers lead us to expect

- Base Qwen2.5-7B-Instruct: owl 0.7%, eagle 7.4%, penguin 0.4% (paper, Figure 3, "Base").
- Paper arm: close to 100% for all three after 3,000 steps (paper, Figures 2 and 9).
- OEL arm: unknown. The paper did not test reverse KL or top-k truncation.

## The loss, and a caveat found while building E0

verl's loss sums over a candidate set of tokens at each position. Without renormalisation, that sum
is not a true divergence when the candidates miss part of the probability (details and a toy
experiment in `bdi/distill/objective.py`). On a toy model where the candidates held only 15% of the
probability, OEL's default loss barely moved the true KL, and forward KL over the student's own
top-k made it three times worse. In E0 the 256 candidates should hold almost everything, because
number tokens are very predictable. To check, every step logs `train/student_mass_in_candidates`
and `train/teacher_mass_in_candidates`; values well below 1 mean the truncation matters. Forward
KL over the student's top-k is refused by the code.

## Running on vast.ai

**Machine.** One H100 80 GB per run. An A100 80 GB also works, more slowly and more cheaply.

- **GPUs to avoid.** B200 and RTX 50-series (Blackwell) need newer CUDA than our pins (torch 2.6,
  CUDA 12.4). 24 GB cards are too small for a 7B model plus vLLM.
- **Driver.** Filter for CUDA 12.4 or newer. The Poetry environment brings its own CUDA libraries;
  the host only needs the NVIDIA driver.
- **Disk.** About 60 GB per run in progress: a full checkpoint holds all base weights in float32,
  about 30 GB. Add 30 GB for the environment and the model download. So about 100 GB for one run
  at a time, or 150 GB for the two main runs side by side.
- **RAM.** About 32 GB per concurrent run: vLLM parks its weights in RAM between generations.
- **Multi-GPU machines.** `scripts/e0.sh 0 1 2 3` runs one queue of runs per GPU.

**Image.** Rent the machine with the Docker image `pabloo22/bdi:<tag>`. It has Python 3.12, Poetry
and the whole `gpu` group installed, so a new machine skips a download of about 15 GB.
`scripts/build_image.sh` builds it from the `Dockerfile`, pushes it and prints the name with its
tag. The tag is a digest of the files the image is built from. Rebuild after changing
`pyproject.toml` or `poetry.lock`; unchanged files give the same tag. Without the image, any image
with Python 3.12 works: run `pip install poetry` first, and the install below then downloads
everything.

**Setup** (the vendored code must be in the repository you clone, so commit `bdi/vendored` first):

```bash
cd /workspace
git clone <your repository> bdi && cd bdi
poetry install --with gpu   # seconds with the image: it adds only bdi itself and the clone's verl
poetry run pytest    # GPU imports, plus the CPU-level wiring tests now on GPU
```

**Smoke test** (Qwen2.5-0.5B-Instruct, 6 steps, a few minutes). It checks that everything runs.
Its timings say nothing about a real run, because the model is 14 times smaller.

```bash
poetry run python -m bdi.distill.run configs/e0/base.yaml configs/e0/smoke.yaml
```

It should end with `runs/e0/smoke-reverse-k256/finished.json`. To check resuming, stop a run
(Ctrl-C) after a checkpoint and start the same command again.

**Pricing a run** (the real 7B setup for 50 steps). Run it on the kind of GPU you plan to rent,
since the time per step depends on the card:

```bash
poetry run python -m bdi.distill.run configs/e0/base.yaml configs/e0/timing.yaml
poetry run python -m bdi.analysis.timing runs/e0/timing-reverse-k256 1.8   # 1.8 = $ per GPU-hour
```

The second command prints the hours and the cost of one full run of 3,000 steps. It adds up the
training steps, the evaluations and the checkpoints, each timed in the short run. Starting up adds
a few minutes per run. The paper's loss scores the whole vocabulary, so it may be slower. To time
it as well, add `objective.direction=forward objective.topk=0` to the first command and use
`runs/e0/timing-forward-k0` in the second.

**E0 itself:**

```bash
scripts/e0.sh            # the two main runs, one after another, on GPU 0
scripts/e0.sh 0 1        # the same, one run per GPU
FOLLOW_UPS=1 scripts/e0.sh 0 1   # also the five follow-ups; finished runs are skipped
poetry run python -m bdi.analysis.e0    # summary table at any time, also for unfinished runs
```

One run alone: `poetry run python -m bdi.distill.run configs/e0/base.yaml teacher.animal=owl`.
Any setting can be overridden the same way, for example
`verl.trainer.logger=[console,wandb]` to log to Weights & Biases.

**Bringing results home** (small, without the large checkpoint files):

```bash
rsync -av --exclude '*.pt' <vast machine>:/workspace/bdi/runs/e0 runs/
```

## What a run writes (`runs/e0/<run name>/`)

Run names read `<animal>-<direction>-k<topk>-s<seed>`; `k0` means the whole vocabulary.

| File | Content |
|---|---|
| `spec.yaml`, `verl_config.yaml` | the resolved run specification and verl config |
| `launches.jsonl` | time, machine and git commit of each start or resume |
| `metrics.jsonl` | one line per step: loss, entropies, candidate mass, timings, evaluations |
| `train_responses.jsonl` | every training prompt and the student's answer |
| `eval/step_<n>_<role>.jsonl` | every evaluation answer, for re-scoring later |
| `checkpoints/global_step_<n>/actor/lora_adapter/` | the trained adapter |
| `finished.json` | written at the end; finished runs are skipped when started again |

Evaluation keys read `eval/<role>/q<questions>/<animal>`. `q50` (all questions, 200 samples each)
is measured at step 0 and at the end; `q10` (the first 10 questions, 50 samples each) at every
evaluation, so it gives one comparable curve. `role` is `teacher` only at step 0.

Training keys worth watching:

- `train/target_mentions`: share of the student's own training answers that name the animal. It
  should stay near 0; otherwise the trait is overt in the text, not subliminal.
- `train/number_format_rate`: share of answers that are plain number lists.
- `actor/policy_loss`: the KL being minimised.
- `timing_s/step`, `timing_s/eval`, `timing_s/save`: seconds spent on one training step, one
  evaluation and one checkpoint.

## Code map

| File | Role |
|---|---|
| `bdi/traits/animals.py` | teacher prompt, the 50 questions, scoring |
| `bdi/data/numbers.py` | the number-sequence prompts |
| `bdi/distill/spec.py` | run specification, and the verl settings our trainer relies on |
| `bdi/distill/objective.py` | the loss variants, as switches of verl's existing loss |
| `bdi/distill/batches.py`, `context.py` | the teacher's view of each student answer |
| `bdi/distill/step.py` | one update: candidates, teacher scores, optimizer step |
| `bdi/distill/trainer.py` | the loop, evaluation, logging, resume and clean-up |
| `bdi/distill/run.py` | the command-line entry point |
| `bdi/analysis/e0.py` | summary tables and curves |
| `bdi/analysis/timing.py` | length and cost of a full run, estimated from a timing run |

The vendored verl code is not modified. `ContextDistillationTrainer` subclasses verl's trainer and
replaces only its training loop.
